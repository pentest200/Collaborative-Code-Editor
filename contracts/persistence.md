# Durable documents (Phase 04)

The worker login inherits only `cce_collab`. It can read the metadata columns needed for room access and replay; it cannot modify tables, read session tokens, or invoke the private guard function. Canonical migration 0004 creates the capability role and scoped SECURITY DEFINER functions with fixed search paths and no PUBLIC execute grants. Provision credentials separately. Compose's `cce_worker` credentials are explicitly local development only.

`cce_append_document` locks `project -> session -> membership -> file -> document -> owner`. This matches Go metadata writes. Project locking serializes quota accounting and metadata changes; session/share and membership/share locks also serialize direct revocation. It verifies the active lifecycle, actor/session, owner/editor role, file/current document/generation, DB-clock live fence, expected head, update size/hash and quota. The identified row and document counter advance in the same transaction. Sequences are bigint internally, decimal strings in JSON and uint64 in binary frames. Authorized duplicates return their original sequence before head/quota checks; a different actor/hash conflicts. Revoked/viewer duplicates cannot obtain receipts.

The configured worker reserves one document with a random process UUID, monotonically increasing fence, 15-second database-clock lease and five-second renewal. Renewal failure closes the room and stops queued writes. The database fence is checked again on every append. A crashed owner leaves its lease until expiry; the statically routed v1 gateway may fail room admission until then. Multi-worker routing remains Phase 10.

Room memory contains encoded committed bytes/vector/head. FIFO candidate work runs in isolated worker threads (two-second deadline, 64 MiB old heap, 8 MiB young heap, four concurrent workers). Hydration, schema validation, full-state encoding and sync-delta construction use the same isolation. Only plain `Y.Text('content')` is allowed. No authoritative state swap, peer update or receipt occurs before committed append success. A lost commit response triggers authorized receipt lookup and room rehydration. If either cannot resolve it, clients get an error/close and no durability claim. Replaying the original identity later is safe. PostgreSQL may complete a statement after its client dies; process death alone does not prove rollback.

Snapshots capture immutable encoded state at a committed head. Automatic publication runs after 100 further updates or approximately 30 seconds of dirty state, and before idle eviction. The snapshot checksum covers encoded Yjs bytes; hydration checks it, the state vector, every replayed update hash and contiguous sequence. `documents.snapshot_id` references a snapshot belonging to that document and never moves backward. A missing/corrupt snapshot/log fails closed rather than starting an empty document or skipping bytes. Replay uses a repeatable-read cut and batches of at most 16 updates (8 MiB); a 30-second hydration budget fails visibly without truncation. Logs are retained, including across snapshots/deletion/generation replacement.

`projects.durable_log_bytes` counts retained update payload bytes across all generations. `durable_log_limit` defaults to 1 GiB, can be lowered by an operator, and cannot exceed 1 GiB. Reaching the limit rejects new updates; duplicate receipts still work. Snapshot/table/index overhead is outside this payload quota and requires disk monitoring/backups. No retention/truncation policy is implemented.

The independent active-source ceiling is 10 MiB (`projects.source_bytes_limit`, operator-lowerable). The isolated validator reports the candidate's UTF-8 size, which append stores in `documents.committed_text_bytes` at the same committed sequence. While holding the project lock, SQL sums that projection for active current-generation documents and substitutes the candidate size before checking the limit. Deleted/replaced generations are excluded automatically; no plaintext content column is introduced. Future restore preparation must initialize the fresh generation's validated size and check the project ceiling in its metadata transaction. Phase 03 persisted only empty initial documents, so the canonical upgrade initializes this size projection at zero.

Rooms have 128 queued operations and 4 MiB queued payload, 100 ingress operations/sec, 256 resident rooms, four concurrent hydrations and a 30-second idle eviction. Oversized/busy work fails explicitly. Existing transport and content ceilings remain in realtime.md; these are limits, not measured capacity claims. Read authorization is revalidated at a two-second interval and before source broadcasts/sync. Data already delivered cannot be erased.

The Phase 04 browser tracks pending identities/hashes in memory and shows Saving until each exact matching receipt arrives. SYNC_STATE yields Synced, never Saved. Access/storage/protocol errors cannot clear pending identities or become Saved. There is no IndexedDB retention, automatic reconnect, retry or draft export until Phase 05. Only server-acknowledged work is covered by restart recovery.
