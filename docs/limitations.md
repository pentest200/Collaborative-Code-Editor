# Current limitations

Phase 03 supports authenticated live editing through Go and a private TypeScript Yjs room. **Edits are volatile.** The worker only reads the generation-one snapshot and holds accepted updates in memory; it does not append them to PostgreSQL. `PENDING_UPDATE` is a temporary peer frame, not a durable receipt. The browser does not persist an outbox. A refresh or tab switch normally replays edits only while the same worker is alive; disconnection before an update is sent, a worker restart, or a browser crash can lose unsaved work. The workspace never displays Saved. Phase 04 must add committed appends, receipts, snapshots, ownership fencing and restart recovery before durable editing is claimed. Phase 05 must add local outbox/reconnect, authenticated awareness, selective undo, and full resource lifecycle behavior.

The initial candidate validator runs in a worker thread with a two-second deadline and a 64 MiB V8 old-generation ceiling, but room state encoding and the validated candidate state application still run in the collaboration process. Phase 04 must measure and harden the complete path under hostile but valid updates. The in-memory room caps pending bytes at 2 MiB; once reached it rejects further edits. The browser has no export path yet, so this is a release blocker for editing valuable work. Connection backpressure closes slow clients; there is no reconnect/outbox recovery until Phase 05. Awareness and shared cursors are not implemented yet.

Phase 03 has no checkpoint, run or search. The project metadata stream replays PostgreSQL events and refetches the tree and role; it polls the database rather than relying on Redis hints. The authenticated browser test uses seeded application sessions because no live GitHub OAuth credentials were supplied; GitHub login itself remains covered by fixture integration tests. The base Compose stack uses development-only credentials and localhost HTTP and is not a production deployment. MinIO, runner, metrics, and scaling services remain later phases.

Go race tests remain unverified on the installed Windows host because its C compiler cannot compile 64-bit mode; ordinary Go tests and vet pass. No throughput, durability, failover, or production-capacity figure is claimed.
